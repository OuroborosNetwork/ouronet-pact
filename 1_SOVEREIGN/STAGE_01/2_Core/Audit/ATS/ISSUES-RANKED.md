#8H — [NOT A BUG] — URC_RBT's abs() masks the -1.0 "uninitialized index" sentinel — Coil/Curl can bootstrap a virgin pool before KickStart, permanently locking out KickStart and opening a genesis inflation-attack / zero-mint-donation path.
　　→ **NOT A BUG, both scenarios closed**, 2026-08-17. Scenario 1 (KickStart lockout): bare-Coil bootstrap on a virgin (index=-1.0) pool is intended — "coil 25 RT, receive 25 RBT, index becomes 1.0; coiling preserves the index, only fueling moves it; fueling doesn't work on -1 pools" (matches the code exactly). KickStart and bare-Coil are alternative, mutually-exclusive bootstrap paths. Scenario 2 (zero-mint donation): refuted after tracing the real mint path — C_Mint → DPTF|C>MINT → DPTF|C>CREDIT → UEV_Amount enforces amount > 0.0 and reverts the WHOLE transaction (Pact atomicity — the earlier RT-in transfer rolls back too), so a depositor whose mint would floor to 0 just gets a clean tx failure, not a silent donation. No code change on either scenario. (Flagged #11M/M2 below for re-check — same premise, not yet re-verified for that specific call path.)

#9H — [FIXED] — UEV_ColdDurationParameters soft branch calls enforce with 3 arguments (Pact's enforce takes exactly 2) — Soft cold-recovery duration can never be set after pair genesis.

Collapsed to a single correctly-formed 2-arg enforce with one `format` call interpolating `base`/`growth`, matching the file's own established convention (`UC_MakeHardIntervals`/`UC_MakeSoftIntervals`, lines 70/95-96). Unit-proven directly against `U|ATS`: hard branch regression guard green, soft branch now accepts valid params (previously crashed unconditionally) and correctly rejects on either of its two mod-conditions. Full-suite reload green, 0 regressions.

#11M — [FIXED] — C_KickStart has no sanity bound on rt-amounts : rbt-request-amount ratio — classic vault inflation-attack setup (relates to #8H).
　　→ Re-examined, 2026-08-17: the original "silent zero-mint donation" framing was partially wrong (an exact-0.0 mint reverts atomically, per #8H's refutation), but the underlying attack survives in the near-zero-but-nonzero regime — a depositor's real RT still gets credited to resident while their RBT rounds down to a negligible fraction of fair value, permanently transferring value to existing RBT holders. **FIXED AND PROVEN** (`ROUND-02-FIXES.md` Fix #7): owner-facing `C_KickStart` now bounded to index ∈ [0.1, 100.0] (0.1 = same floor as syphon); new admin-facing `A_KickStart` (module governance, not pool ownership) keeps the 0.1 floor but has no ceiling, for legitimate higher ratios. Layered per StoicSyntax §14.7 (unevented core + 2 named event leaves), mirroring the existing RemoveSecondary precedent. 8/8 assertions green against the real deployed capabilities (test-capability, real signatures) — pure-math boundaries, owner ceiling/floor rejection, admin floor-still-applies, admin no-ceiling.

#12M — [NOT A BUG] — XE_UpdateRUR has no floor-at-zero on any of its three buckets (resident/unbonding/royalty); backstopped today by a constructor-level enforce (>= 0.0), but no defense-in-depth at the source.

#17M — [NOT A BUG] — UC_SplitByIndexedRBT has no zero-guard on resident-sum — reachable division-by-zero abort (DoS on preview/quote flows).
　　→ **NOT A BUG**, owner confirmed 2026-08-17. Proved the invariant mathematically from `URC_Index`'s own formula: `index = if rbt-supply=0.0 then -1.0 else floor(resident-sum/rbt-supply, p)`. `resident-sum = 0.0` (with nonzero rbt-supply) is the *only* way `index` reads exactly `0.0`; `rbt-supply = 0.0` is the only way it reads `-1.0`. So whenever `index` is strictly positive (not `0.0`, not `-1.0`), `resident-sum` is guaranteed nonzero by construction of the formula - the division-by-zero literally cannot fire. Owner: "so long as index... is non zero or non negative, the resident amount can never be 0... that's why I never added such an enforcement." Confirmed correct. Noted (not a blocking concern, no action taken): no caller of `UC_SplitByIndexedRBT`'s chain explicitly checks `index > 0` before calling in - the safety today rests on the protocol keeping resident-sum/rbt-supply in lockstep (the same kind of invariant #2C's fix was about), not on this function protecting itself. Closed without a code change.
