#8H — [NOT A BUG] — URC_RBT's abs() masks the -1.0 "uninitialized index" sentinel — Coil/Curl can bootstrap a virgin pool before KickStart, permanently locking out KickStart and opening a genesis inflation-attack / zero-mint-donation path.
　　→ **NOT A BUG, both scenarios closed**, 2026-08-17. Scenario 1 (KickStart lockout): bare-Coil bootstrap on a virgin (index=-1.0) pool is intended — "coil 25 RT, receive 25 RBT, index becomes 1.0; coiling preserves the index, only fueling moves it; fueling doesn't work on -1 pools" (matches the code exactly). No code change on either scenario. (Flagged #11M/M2 below for re-check — same premise, not yet re-verified for that specific call path.)

#17M — [NOT A BUG] — UC_SplitByIndexedRBT has no zero-guard on resident-sum — reachable division-by-zero abort (DoS on preview/quote flows).
　　→ **NOT A BUG**, owner confirmed 2026-08-17. Proved the invariant mathematically from `URC_Index`'s own formula: `index = if rbt-supply=0.0 then -1.0 else floor(resident-sum/rbt-supply, p)`. `resident-sum = 0.0` (with nonzero rbt-supply) is the *only* way `index` reads exactly `0.0`; `rbt-supply = 0.0` is the only way it reads `-1.0`. So whenever `index` is strictly positive (not `0.0`, not `-1.0`), `resident-sum` is guaranteed nonzero by construction of the formula - the division-by-zero literally cannot fire. Owner: "so long as index... is non zero or non negative, the resident amount can never be 0... that's why I never added such an enforcement." Confirmed correct. Noted (not a blocking concern, no action taken): no caller of `UC_SplitByIndexedRBT`'s chain explicitly checks `index > 0` before calling in - the safety today rests on the protocol keeping resident-sum/rbt-supply in lockstep (the same kind of invariant #2C's fix was about), not on this function protecting itself. Closed without a code change.
