Worth recording because it decides the backfill arithmetic. `SubsidiaryTreasury` has **26
present users** and **5 member score entities**, and its WSTOA counter reads 29 against 27
positive legs. A per-account counter could not exceed 26. So `unclaimed-count` counts
`(user, member)` legs — matching S1 §2's definition and the user's original intent.

## 3 — What the fix transactions therefore need

**Good news: no new tooling is required to compute the backfill values.** The target figure for
every lane is already readable live — `URHC_BuildEvictPlans` yields the positive-claimable leg
count, which is the S1 §2 definition. The 11 rows in §2 ARE the backfill worklist.

Two cautions carried from S1 §7:

1. **The values are live and move.** They must be re-read at round-construction time, not copied
   from this file. This scan is evidence that the defect exists and sizing for the round; it is
   not the payload.
2. **Ordering is load-bearing.** The backfill must land after the modules and before any inject
   or collect on that lane. A lane injected in the gap reads a default and the first collect
   sweeps the whole lane to one account.

One practical note: `URHC_BuildEvictPlans` on `OuroLpFarm` **exceeds a 1,000,000 gas local
limit** (measured 1,019,573) and needs a raised limit to read at all. A round-construction tool
must not assume the default local budget suffices.

## 4 — F4: the `coin` UrStoa vault, measured on mainnet

### 4.1 — CORRECTION: the vault is restricted to ChainId 0, not chain 1

The plan of record was *"the fix transactions for the coin module will execute only on chain 1"*.
**The contract refuses that.** Reading any vault function on chains 1–9 returns:

```
UR-STOA Operations are restricted to ChainId 0
```

So the vault rows live on **chain 0** and nothing else can hold them. The module still deploys to
all 10 chains (it is `coin`), but **every fix transaction must target chain 0**. Verified by
reading `UR_URV|VaultSupply` on each of the ten chains.

### 4.2 — The S1 defect is live here, and the counter is wrong by its OWN definition

One atomic read (a single `/local` expression, so no timing skew between the parts):

| | |
|---|---|
| accounts in `URV\|UrStoaVaultUser` | **6** |
| `unclaimed-count` | **6** |
| `nzs-count` | **5** |
| `stoa-supply` (claimable) | `81498.817653777542` |
| Σ owed (`pending + (crps − last-rps) × supply`) | `81498.737058332521` |
| **residue** | **`0.080595445021` STOA** |

Two separate facts, and the first is sharper than `SPEC-coin-urstoa-vault.md` claimed:

1. **The counter is wrong even under the permissive meaning it implements.** Six accounts hold
   rows; five have non-zero stake; the sixth (`k:9ea91a7a…`) has **stake 0 and pending 0** — it can
   never claim anything. Under the *current* superset definition ("accounts that can ever claim")
   the correct value is **5**. It reads 6. So this is not only a disagreement between the doc and
   the writer — a decrement that should have fired did not, and the row has been counted ever
   since. The spec said "five stakers, so the count never falls to 1"; measured, the count is 6
   against 5 stakers, and the extra is a stale row.

2. **The residue is material, not sub-unit.** `0.0806 STOA`. The AQP lanes strand single-digit
   sub-units; this is eight hundredths of a token, because coin's vault carries 250,001 URSTOA of
   stake and an RPS in the tens of thousands, so each flooring event loses far more than one
   sub-unit. The sweep that would mop it up requires `unclaimed-count = 1` and the counter sits
   at 6, so it is unreachable — the same terminal state as the three AQP lanes in §2.2.

### 4.3 — Method note, because the first attempt was wrong

The residue was first computed from **sequential** `/local` calls and came out at `0.080596`,
while `claimable` moved across the reads (`81496.657901` → `81498.277716` → `81498.817654`). The
vault takes injections, so any figure assembled from several round-trips mixes two states and the
difference cannot be distinguished from a real residue. Recomputed as **one Pact expression** that
reads `current-rps`, the claimable total and every user row inside a single evaluation, then
repeated: `0.080595445021` **both times, to the last digit**. Only the atomic form is evidence.
A round-construction tool must read each lane's figures in one expression for the same reason.

## 5 — D3: the multiplier path, and a sixth finding

`SCR|C>UPDATE-MULTIPLIERS` was traced for F1's defect. **Verdict: PRESENT on the
`mx-hibernated` leg, structurally ABSENT on `mx-frozen` and `mx-sleeping`.** Recorded as **F6**
in [`FINDINGS-2026-11-08.md`](FINDINGS-2026-11-08.md).

### 5.1 — The stamped ledger does NOT protect against a multiplier change

This is the part worth stating precisely, because the obvious reading is the wrong one.
`URC_SignedBaseDeltaForSpecialDpofStake` delegates to
`URC_SCR|SleepingLegWeight … (not direction)`, and `from-ledger` looks like the "stamp and
reverse" mechanism that would make the round trip exact. It is not. The function says so:

> `from-ledger` **SELECTS THE CLOCK, AND ONLY THE CLOCK.**

`mx-ceiling` is bound **outside** that branch:

```pact
(mx-ceiling:decimal
    (if (= cap-months CT_HIBERNATE_MONTHS)
        (UR_SCR|ScoreMxHibernated score-id)      ;; LIVE on both legs
        (UR_SCR|ScoreMxSleeping   score-id)))
```

So the ledger stamps the **term**, never the **multiplier**. No special leg is protected from a
multiplier change by the stamp — all three are protected only by the **gate**, and the gate scans
two of the three. That reframes F1: the stamped-ledger precedent cited in
`SPEC-score-definition-reissue.md` §12.1 as "Family A already exists in the tree" is narrower than
it appeared — it solves clock drift, not multiplier drift.

### 5.2 — The gate scans frozen and sleeping, never hibernation

`UEV_AQP|ScoreMxChangeSafe` → `URC_AQP|ScoreMxChangeSafe` (`03_AQP.pact:1250`) reads
`ref-DPTF::UR_Frozen` and `ref-DPTF::UR_Sleeping` and checks each tracker is empty.
**`UR_Hibernation` occurs exactly once in all of `03_AQP.pact`** — at line 1949, the admission
check — and never in the gate. Verified by count, not by reading.

The `H|` leg is live: `URC_StakeOrtoFungibleDpofMatchesPool` admits it on **aqp-class 1**
(`03_AQP.pact:1946-1949`), `URC_OrtoDpofUsesSleepingMultiplier` returns **false** for `H|` so it
selects `mx-hibernated`, and `UC_MxForRemaining` returns `mx-ceiling` **flat** for hibernation —
no decay to damp the delta. `UEV_Fee` admits `[1.0 .. 999.0]`.

Residue: `floor(q × mx_H1) − floor(q × mx_H2)` on the stored base, unbounded in magnitude and
sign, up to ~998× the staked amount from a single change. Strictly worse than the sleeping case,
where the 300-month decay damps the term.
